Add Instrumentation

Configuration

The 'Add Instrumentation' filter is enabled by specifying:

Apache:
ModPagespeedEnableFilters add_instrumentation
Nginx:
pagespeed EnableFilters add_instrumentation;

in the configuration file.

Description

The 'Add Instrumentation' filter injects two small blocks of JavaScript into every HTML page. Together they implement real-user monitoring: they measure how the page actually loaded and rendered for the visitor— including the Core Web Vitals (Largest Contentful Paint, Cumulative Layout Shift, and Interaction to Next Paint)—and report the measurements back to the server.

Operation

An empty HTML file passed through the add_instrumentation filter will come out like this (the inserted whitespace is for documentation readability; the collector script is abbreviated): 

<html>
  <head>
    <script>
      window.mod_pagespeed_start = Number(new Date());
  </script>
  </head>
  <body>
    <script>
      (function(){/* Core Web Vitals collector */})();
      pagespeed.addInstrumentationInit(
          '/mod_pagespeed_beacon', '', 'http://example.com/');
    </script>
  </body>
</html>

Example

You can see the filter in action at www.modpagespeed.com on this example.

Methodology

The first script tag is inserted at the beginning of the document's <head>. It simply records the current time in a global variable. This is placed as early in the document as possible in order to best approximate the beginning of the page load, and serves as the timing fallback on browsers without Navigation Timing support.

The second script tag is inserted at the end of the document's <body>, so as to minimally interfere with page rendering. It observes the page through PerformanceObserver (with buffered delivery, so events from before the script ran are included), collecting:

  • LCP—Largest Contentful Paint, in milliseconds.
  • CLS—Cumulative Layout Shift, using the standard session-window definition (windows of at most 5 seconds, gaps of at most 1 second; the worst window is reported). To keep the beacon integer, the value is reported in milli-units: a CLS of 0.1 arrives as cls=100.
  • INP—the worst interaction latency observed, in milliseconds.
  • Navigation Timing Level 2 data: time to first byte (reported as the c_ttfb parameter; the legacy ttfb parameter measured a different interval and is ignored), DNS, connect, download, and DOM-content-loaded timings, plus the total load time. The navigation-type parameter nt= now carries the Navigation Timing string type (navigate/reload/back_forward) rather than the old numeric code.

The collected metrics are sent once per page view, when the page is hidden or unloaded (visibilitychange to hidden, or pagehide). Reporting at page-hide rather than at onload means the numbers are final—late layout shifts and interactions are included—and pages abandoned before onload are still reported. The report is a single navigator.sendBeacon POST whose body carries the metrics as query parameters; browsers without sendBeacon fall back to a GET request with the same parameters in the query string. On browsers without PerformanceObserver or Navigation Timing support the beacon degrades gracefully, carrying whichever subset can be measured. The collector deliberately registers no beforeunload or unload handlers: those disable the browser's back/forward cache.

The ReportUnloadTime directive is deprecated and has no effect: it used to inject a second, beforeunload-driven beacon for pages abandoned before onload. The page-hide trigger covers that case without breaking the back/forward cache. Configurations that still set the option keep parsing.

By default, the target of the beacon is the relative URL "/mod_pagespeed_beacon" (Apache) or "/ngx_pagespeed_beacon" (Nginx). PageSpeed handles these results itself and simply returns "204 No Content" which should cause minimal disruption for the client. It also records the number of beacons, and the total of their load times, in the statistics "page_load_count" and "total_page_load_ms". These are visible on the PageSpeed statistics page (which, by default, is only viewable from the server's localhost). You can divide total_page_load_ms by page_load_count to get the average load time for your site. The Core Web Vitals are aggregated into four histograms on the statistics/admin pages—Beacon Reported LCP (ms), Beacon Reported CLS (milli-units), Beacon Reported INP (ms), and Beacon Reported TTFB (ms)— alongside the existing Beacon Reported Load Time (ms) histogram, so you can read percentiles rather than just averages.

One-time note for deployments upgrading from the legacy collector: the ets=load: value behind total_page_load_ms and the Beacon Reported Load Time (ms) histogram changed meaning. It used to measure load-event time minus the head timing script's execution time; it is now the Navigation Timing loadEventStart, measured from navigationStart, so it additionally includes DNS lookup, connection setup, and time to first byte. Expect a one-time upward shift in that histogram and in the computed average load time at rollout—a level change, not a regression—and compare averages only within the same collector generation.

You can change the location of the beacon to a different path (or even a different server) using the BeaconUrl directive. For example:

Apache:
ModPagespeedBeaconUrl "/my/path/to/beacon"
Nginx:
pagespeed BeaconUrl "/my/path/to/beacon";

Or, if you want to set up your own beacon server somewhere else, you can use:

Apache:
ModPagespeedBeaconUrl "http://my.other.server/my_beacon"
Nginx:
pagespeed BeaconUrl "http://my.other.server/my_beacon";

If you want to set an https beacon URL that is different from the http beacon URL (for example a different machine as shown below, or a non-default port), you can do so by separating the http and https URLs with a space. You don't need to do this if the beacon URLs only differ in protocol (http versus https):

Apache:
ModPagespeedBeaconUrl "http://insecure.server/my_beacon https://secure.server/my_beacon"
Nginx:
pagespeed BeaconUrl "http://insecure.server/my_beacon https://secure.server/my_beacon";

Note that the BeaconUrl used to require that custom beacon URLs end with "?ets=". Appending the query param to the custom URL is no longer required and should be removed if present.

Every beacon shows up in your webserver access.log along with the timestamp, IP address, and user-agent, and the logged query string carries the url= parameter identifying the measured page—so the log tells you when, where, and for which page a measurement was taken. The metrics themselves travel in the POST body, which webservers do not log by default; for aggregate analysis (percentiles, historical behavior) use the beacon histograms on the PageSpeed statistics/admin pages, or point BeaconUrl at your own collection endpoint and process the POST bodies there.

Requirements

The "Add Instrumentation" filter requires the "Add Head" filter, and will enable it automatically.

Risks

This filter could break pages if they include JavaScript which depends on knowing the first child of the <head> or the last child of the <body>.

The injected JavaScript is very lightweight, and should cause only a very tiny (though nonzero) amount of extra load on the client.

If you already have a client-side latency measurement system in place (such as Jiffy, Episodes, or Boomerang), you probably don't need this filter.

On browsers without Navigation Timing support the reported data is only approximate and does not include time the client spends resolving your domain, opening a connection, and waiting for the first few bytes of HTML; modern browsers report those phases explicitly.
