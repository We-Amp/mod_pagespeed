Prioritize Critical Images

Configuration

The 'Prioritize Critical Images' filter is enabled by specifying

Apache:
ModPagespeedEnableFilters prioritize_critical_images
Nginx:
pagespeed EnableFilters prioritize_critical_images;
in the configuration file.

Objective

Improve Largest Contentful Paint by raising the fetch priority of the images that render above the fold, so the browser frontloads the fetches that determine when the page appears complete.

Description

The prioritize_critical_images filter adds fetchpriority="high" to <img> elements that a beacon has reported as visible in the client's initial viewport (above the fold). Browsers schedule such images ahead of other resources, which typically moves the largest above-the-fold image — the Largest Contentful Paint candidate — earlier in the load.

Criticality is keyed on the image's src attribute URL: the beacon instrumentation stamps a hash of the resolved src on each <img>, and the beacon reports the stamped URLs of the images seen in the initial viewport. For responsive images this still raises the right fetch: per specification, fetchpriority on the <img> applies to whichever srcset candidate the browser selects, so annotating on a critical src also prioritizes a selected srcset candidate. Images with no src at all (srcset-only markup) are eligible too, keyed on the candidate the browser actually displays: the beacon stamps the hashes of all srcset candidates and reports the one matching currentSrc, and the filter annotates the element when any of its candidates is critical.

fetchpriority="high" is a scarce signal: every prioritized fetch competes with render-critical resources. The filter therefore annotates at most 2 images per page, in document order. An image whose author already set fetchpriority="high" counts against that budget. Duplicate <img> tags referencing the same critical URL each count against it as well, even though browsers coalesce them into a single fetch. The budget governs only this filter; it is not a page-wide guarantee. In particular, when lazyload_images also runs in native mode (ModPagespeedLazyloadImagesMode), that filter adds fetchpriority="high" to every beacon-critical image it keeps eager, with no cap, so the page can end up with more than two high-priority images in total.

Beacon dependency

This filter relies entirely on critical-image beaconing: enabling it instruments the page with the critical-images beacon JavaScript, and it takes a few accesses of a page for the beacon data to be reported back and processed. Until the data is available the filter is a strict no-op — it never guesses which images are critical, because raising the priority of a below-the-fold image would slow down the images that matter.

If beaconing is disabled with the ModPagespeedCriticalImagesBeaconEnabled directive, no data ever arrives and the filter remains inactive.

Author markup

An author-supplied fetchpriority attribute always wins, whatever its value: the filter never modifies or overrides it. As noted above, an author fetchpriority="high" does consume one slot of the 2-image budget.

Save-Data

For requests carrying the Save-Data header the filter is disabled (when Save-Data support is active): a client asking to conserve data should not have image fetches frontloaded.

Example

The effect of this filter can be observed by comparing the image request priorities before and after rewriting. After the beacon data for the page has been collected, the above-the-fold image carries fetchpriority="high".

Risks

This filter is considered low risk: it only adds an attribute, injects no scripts of its own beyond the beacon instrumentation, and does nothing until beacon data is available. If a page's layout changes so that previously beaconed images move below the fold, they may briefly keep their raised priority until fresh beacon results replace the stale data.
