The worker exposes an HTTP/1.1 API for monitoring, cache management,
configuration, and browser-based analysis. The [web console](/docs/workbench/)
is built on this API, so anything the console shows you can also read or drive
yourself. Every endpoint documented here works with `curl` or any HTTP client.

## Base URL

The API listens on `127.0.0.1:9880` by default. Configure with `--api-port`.
Set port to `0` to disable the HTTP API entirely.

```text
http://127.0.0.1:9880/v1/...
```

:::note[In-process ASP.NET Core middleware]
The `:9880` examples throughout this page describe the **standalone worker**.
With the in-process ASP.NET Core middleware
([`WeAmp.PageSpeed.AspNetCore`](/docs/aspnet-getting-started/)), the
`/console/` and `/v1/*` surfaces are served on **your app's own port** — the
port your ASP.NET Core app listens on (e.g. `http://localhost:5123/console/`)
— not on `:9880`. The worker's own HTTP API stays bound to `127.0.0.1` on an
ephemeral loopback port unless you set `Worker.ApiPort` explicitly. Substitute
your app's origin for `localhost:9880` in the examples below. There is no
authentication on these paths by default and the worker API token does not
apply; see [Console](/docs/aspnet-configuration/#console-pagespeedconsole) to
turn them off or gate them.
:::

All endpoints are prefixed with `/v1/`. The server supports HTTP/1.1 only
(no HTTP/2). Keep-alive connections are supported.

### Server limits

| Parameter        | Default | Flag                |
| ---------------- | ------- | ------------------- |
| Max connections  | 128     | `--max-connections` |
| Request timeout  | 10s     | -                   |
| Max request body | 64 KB   | -                   |
| Max URL length   | 8192    | -                   |
| Max header bytes | 64 KB   | -                   |

## Transports

The API is off until you enable a transport, and there are two.

`--api-socket [PATH]` serves HTTP/1.1 over a unix socket (default
`/run/pagespeed-optimizer/api.sock`, mode 0660 `pagespeed:pagespeed`). This is
the recommended local transport: filesystem permission is the credential, so a
peer in group `pagespeed` needs no token — for reads and for cache purge
alike — and the worker binds no TCP port at all. A connection accepted on the
socket is an authenticated peer; a token configured alongside it does not
reimpose a bearer requirement.

Peers on the socket must still send `X-Requested-With: XMLHttpRequest` on
mutating requests (POST/PATCH). Reverse-proxying the console onto this socket
is a supported topology, and through such a proxy a browser can reach it
cross-origin — with no credential in the chain — so that header is the control
that keeps a cross-origin POST from purging your cache. Reads need nothing.

```bash
curl --unix-socket /run/pagespeed-optimizer/api.sock http://localhost/v1/stats
```

The `--api-socket` transport is also the surface the web server module's
unified console reads: its worker panels proxy `GET /v1/health`,
`GET /v1/stats`, and `GET /v1/cache/cooldowns` over this socket. The console
panels require a 2.1.0 worker or later; against an older or unreachable worker
the panel reports it as such instead of failing the console.

`--api-port PORT` binds TCP, `127.0.0.1` by default.

## Authentication

A token is set with the `PAGESPEED_API_TOKEN` environment variable (preferred —
`--api-token` puts the credential on the command line, where any local user can
read it out of `/proc/<pid>/cmdline`). With a token configured, every endpoint
except `/v1/health` and the `/console/` static bundle (GET/HEAD only) requires
a Bearer header.

```bash
curl -H "Authorization: Bearer <your-token>" http://localhost:9880/v1/stats
```

### The invariant

**Remote is never unauthenticated, and unauthenticated is never remote.** The
worker checks this while parsing its configuration and refuses to start rather
than serve a combination that breaks it. Each refusal names the flag that would
make the requested posture legal.

| Transport        | Token   | Extra flag           | Result                             |
| ---------------- | ------- | -------------------- | ---------------------------------- |
| unix socket      | either  | —                    | normal — no token is asked for     |
| TCP loopback     | present | —                    | normal                             |
| TCP loopback     | absent  | `--api-no-auth`      | allowed, warning banner at startup |
| TCP loopback     | absent  | —                    | **refuses to start**               |
| TCP non-loopback | present | `--api-allow-remote` | allowed, warning banner            |
| TCP non-loopback | present | —                    | **refuses to start**               |
| TCP non-loopback | absent  | any                  | **refuses to start**               |

Also refused at startup: `--api-socket` together with `--api-port` (one
transport only), and an `--api-bind` that is not an IPv4 literal (`localhost`
and `::1` included — the API binds IPv4 only).

### Authentication modes

| Mode                       | Behavior                                          |
| -------------------------- | ------------------------------------------------- |
| Unix socket                | All endpoints open to peers in group `pagespeed`  |
| Token configured (TCP)     | All endpoints require auth (except `/v1/health` and the `/console/` static bundle) |
| Token + `--api-read-open`  | An explicit allow-list of GET routes + the `stats`/`events` WebSocket streams open (except the log: `GET /v1/logs`, `/v1/ws/logs`), POST/PATCH require auth |
| No token + `--api-no-auth` | All endpoints open — TCP loopback only            |

In read-open mode (`--api-read-open`), an explicit allow-list of GET
endpoints and WebSocket streams is accessible without authentication.
Concretely: the cached-URL inventory (`GET /v1/cache/urls`), per-URL variant
detail and content (`GET /v1/cache/alternates`, `/select`, `/content`) —
which is also where the origin hosts and content types behind each cached
URL are visible — the active cooldown table (`GET /v1/cache/cooldowns`),
overall stats/metrics/config (`GET /v1/stats`, `/v1/metrics`, `/v1/config`),
and the live `/v1/ws/stats` and `/v1/ws/events` WebSocket streams. This
enables exposing the console publicly as a read-only dashboard while keeping
mutating operations (config changes, cache purge) behind the token. Auth for
WebSocket is sent as the first message (see
[WebSocket Endpoints](#websocket-endpoints)). The one exception is the optimizer
log: log lines carry the URLs, origin hosts and error text of every site the
optimizer serves, so `GET /v1/logs` still requires the token on TCP, and the
`/v1/ws/logs` stream requires it too — send it as the first message after the
handshake (see [WebSocket Endpoints](#websocket-endpoints)), since a browser
cannot carry the token on the handshake itself.

`--api-read-open` is an explicit allow-list, not an opt-out. In earlier
releases an *absent* token opened reads as a side effect; it no longer does,
and an unset token now fails closed on every endpoint that is not
`/v1/health` or the `/console/` static bundle. The allow-list is also
closed by default for anything new: a GET route added in a later release
stays behind the token under read-open unless it is deliberately added to
the list, so the read-only surface never grows silently.

Because read-open still exposes real operational data about your sites,
only enable it behind a reverse proxy that performs its own
authentication (IP allow-listing, a login prompt, etc.) — never expose it
directly to the open internet.

### Error responses

When auth fails, the API returns:

- **401** `UNAUTHORIZED` -- Missing `Authorization` header or wrong scheme
- **403** `FORBIDDEN` -- Invalid token

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Authentication required"
  }
}
```

## CORS

The API sends no CORS headers, and no flag or config key turns them on, so a
browser page on another origin cannot call it. Use the web console at
`/console/`, call the API from a server-side client, or put a reverse proxy in
front that serves your page and the API from one origin.

`serve_savings` and `serve_classes` are present when serve-time statistics are
available (the shared `.pagespeed-serve-stats` file). The `serve_savings` byte
counters are measured by the serving front end (nginx, the ASP.NET middleware,
or the module) as content is served, so they reflect
realized bandwidth savings and are distinct from the worker-side `by_type`
counters above. `serve_classes` partitions the serves a front end judged
optimizable into exactly one class each; today only the module
classifies serves, so under another front end the block reads all-zero —
which means "not instrumented", not "nothing happened".

`serve_savings_by_host` attributes the same HITs to the host each response was
served for, when the front end names one. The optimizer reports a host under
its host name: ASCII letters are lowercased, and a `:port` (1–5 digits) and one
trailing `.` are dropped, so `WWW.Example.com:8443` and `www.example.com.` are
both reported as `www.example.com`. What is left must be 1–127 bytes with at
least one letter or digit, made of letters, digits, `.`, `-` and `_` (a DNS
name or an IPv4 address such as `10.1.2.3`), or an IPv6 literal in brackets of
hexadecimal digits, `:` and `.` (`[2001:db8::1]`; an IPv6 address without
brackets is not accepted). Any other value — empty, longer, containing any
other character, with a malformed bracket, or still ending in `.`
(`www.example.com..`) — is never stored or reported: that HIT counts under
`other`. The optimizer keeps a row for each of the first 64 distinct hosts it
sees after it starts and reports up to 32 of them, ordered by HITs; a host seen
after those 64 counts under `other` until the optimizer restarts. The hosts and
`other` together add up to the `serve_savings` totals.

### GET /v1/metrics

Worker statistics in Prometheus text exposition format. Suitable for direct
Prometheus scraping.

```bash
curl http://localhost:9880/v1/metrics
```

**Response** (`Content-Type: text/plain; version=0.0.4; charset=utf-8`):

```text
# HELP pagespeed_notifications_total Total notifications received.
# TYPE pagespeed_notifications_total counter
pagespeed_notifications_total 4821
# HELP pagespeed_variants_written_total Total variants written to cache.
# TYPE pagespeed_variants_written_total counter
pagespeed_variants_written_total 2106
# HELP pagespeed_cache_entries Current number of cache entries.
# TYPE pagespeed_cache_entries gauge
pagespeed_cache_entries 3412
...
```

All counters and gauges from `/v1/stats` are exposed as Prometheus metrics,
including SVG stats, learned quality, content analysis, and browser analysis
counters.

Serve savings per host are `pagespeed_host_hits_served_total`,
`pagespeed_host_original_bytes_served_total` and
`pagespeed_host_optimized_bytes_served_total`, labelled `host` with the host
names `serve_savings_by_host` reports (the same host-name rule); the rest is
`host="(other)"`, a value no host name can take.

### PATCH /v1/config

Update hot-reloadable configuration fields at runtime. Only fields included in
the request body are changed. Changes are persisted to disk alongside the cache
volume. The response is sent once the change is saved; if saving fails, the
change stays in force until the next restart and `warnings` says so.

While the save runs, the worker keeps serving other requests. If the save takes
longer than the request timeout, the request is answered `504` and the
connection is closed, but the change is already in force and is written to disk
when the save finishes; a failed save is reported in the worker log. Read `GET /v1/config` to confirm the current values.

```bash
curl -X PATCH http://localhost:9880/v1/config \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"jpeg_quality": 80, "svg_mode": "auto"}'
```

**Request body:** JSON object with one or more config fields to update.

**Response:**

```json
{
  "applied": {
    "jpeg_quality": 80,
    "svg_mode": "auto"
  },
  "rejected": {},
  "warnings": [],
  "config": { ... }
}
```

| Field      | Description                                        |
| ---------- | -------------------------------------------------- |
| `applied`  | Fields that were accepted and applied              |
| `rejected` | Fields that failed validation, with error messages |
| `warnings` | Non-fatal warnings about the applied configuration |
| `config`   | Full configuration after applying changes          |

Fields that fail validation are rejected individually. Valid fields in the same
request are still applied. All boolean toggle fields (`disable_async_css`,
`disable_script_deferral`, etc.) are hot-reloadable via `PATCH /v1/config`.

```json
{
  "applied": {
    "jpeg_quality": 80
  },
  "rejected": {
    "jpeg_quality_invalid": "unknown field"
  },
  "warnings": [],
  "config": { ... }
}
```

## Cache operations

### GET /v1/cache/urls

Paginated list of all cached URLs. The worker tracks URLs in memory as they are
processed.

```bash
curl "http://localhost:9880/v1/cache/urls?offset=0&limit=50"
```

**Query parameters:**

| Parameter  | Type   | Default | Description                            |
| ---------- | ------ | ------- | -------------------------------------- |
| `offset`   | int    | 0       | Skip this many entries                 |
| `limit`    | int    | 100     | Max entries to return (capped at 1000) |
| `hostname` | string | -       | Filter by hostname                     |

**Response:**

```json
{
  "urls": [
    {
      "url": "/images/hero.jpg",
      "hostname": "example.com",
      "alternate_count": 12
    },
    {

    }

  "limit": 50,
  "next_offset": 50,
  "has_more": true,
  "total": 342
}
```

### POST /v1/cache/purge

Delete cached variants for a URL, or purge the entire cache. Like every
`POST` or `PATCH` under `/v1/`, a purge sent over the unix socket, or to a TCP
API without a token, must carry `X-Requested-With: XMLHttpRequest`; without it
the optimizer answers 400. The examples on this page send it, which does no
harm when a token is configured.

**Single URL purge:**

```bash
curl -X POST http://localhost:9880/v1/cache/purge \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"url": "/images/hero.jpg", "hostname": "example.com"}'
```

**Response:**

```json
{
  "url": "/images/hero.jpg",
  "hostname": "example.com",
  "deleted": 12
}
```

When `deleted` is `0`, the response includes a note explaining the URL was not
found in cache.

A purge without a `site` reaches the URL's entries for every site (nginx
server block) the optimizer has received a request notification from; an
entry stored by a server block it has not heard from stays until it expires
or a full purge removes it.

**Full cache purge:**

Purge all cached content. This stops the cache, deletes the volume file, and
recreates it from scratch. Requires explicit confirmation.

```bash
curl -X POST http://localhost:9880/v1/cache/purge \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"scope": "all", "confirm": "purge-all"}'
```

**Response:**

```json
{
  "scope": "all",
  "urls_cleared": 342,
  "volume_reset": true
}
```

Omitting the `confirm` field or providing the wrong value returns a 400 error.

### POST /v1/cache/reprocess

Clear the dedup set and cooldown for a URL, then enqueue it for reprocessing.
Unlike purge, this does not delete the cached content. The worker re-reads the
original from cache and regenerates all optimized variants.

```bash
curl -X POST http://localhost:9880/v1/cache/reprocess \
  -H "Content-Type: application/json" \
  -H "X-Requested-With: XMLHttpRequest" \
  -d '{"url": "/style.css", "hostname": "example.com"}'
```

**Response:**

```json
{
  "url": "/style.css",
  "hostname": "example.com",
  "reprocess_enqueued": true
}
```

### GET /v1/cache/cooldowns

List all URLs currently in a processing cooldown. Cooldowns prevent tight
re-processing loops for the same URL.

```bash
curl http://localhost:9880/v1/cache/cooldowns
```

**Query parameters:**

| Parameter  | Type   | Required | Description        |
| ---------- | ------ | -------- | ------------------ |
| `hostname` | string | No       | Filter by hostname |

**Response:**

```json
{
  "cooldowns": [
    {
      "url": "/index.html",
      "hostname": "example.com",
      "reason": "revalidation",
      "remaining_seconds": 2,
      "duration_seconds": 3
    },
    {
      "url": "/about.html",
      "hostname": "example.com",
      "reason": "tentative",
      "remaining_seconds": 45,
      "duration_seconds": 60
    }
  ],
  "count": 2,
  "enabled": true

```

**Cooldown reasons:**

| Reason          | Duration | Description                                                                |
| --------------- | -------- | -------------------------------------------------------------------------- |
| `tentative`     | 60s      | Processing in progress; prevents concurrent threads from duplicating work  |
| `write_failure` | 60s      | Cache write failed (reader contention on mmap handles)                     |

## Logs

### GET /v1/logs

Recent log entries from the optimizer's in-memory log (the same 2,000-entry
ring the [`/v1/ws/logs`](#get-v1wslogs) stream starts from), for clients that
poll over plain HTTP.

Over TCP this endpoint requires the API token even in read-open mode (see
[Authentication Modes](#authentication-modes)); over the unix socket it is
open to peers in group `pagespeed` like every endpoint.

```bash
curl "http://localhost:9880/v1/logs?limit=100"
curl "http://localhost:9880/v1/logs?since=1841"
```

**Query parameters:**

| Parameter | Type | Default | Description |
| --------- | ---- | ------- | ----------- |
| `since`   | int  | -       | Return entries with a `seq` above this, oldest first. Without it, the newest entries. |
| `limit`   | int  | 500     | Max entries to return (capped at 500; `0` means the default) |

A page is also at most 512 KiB of JSON: a page of long lines holds fewer
entries, and `more` says when to read again.

**Response:**

```json
{
  "entries": [
    {
      "level": "info",
      "message": "cache flush complete",
      "module": "worker",
      "seq": 1842,
      "source": "worker",
      "timestamp": 1759230000000,
      "type": "log"
    }
  ],
  "gap": false,
  "more": false,
  "newest_seq": 1842,
  "next_since": 1842,
  "oldest_seq": 1,
  "shed_total": 0,
  "stream_id": "9f2c4e1a7b3d5c80"
}
```

| Field        | Description |
| ------------ | ----------- |
| `entries`    | Log entries, ascending by `seq`. The entry fields are the ones [`/v1/ws/logs`](#get-v1wslogs) sends. |
| `next_since` | Pass this as `since` on the next read. |
| `more`       | Newer entries are waiting beyond this page: read again now. |
| `gap`        | Entries between your `since` and `oldest_seq` were dropped from the ring before you read them. |
| `oldest_seq` / `newest_seq` | The oldest and newest entry the ring still holds. |
| `shed_total` | Entries not recorded because the optimizer was logging faster than it could keep; increases over the process's life. |
| `stream_id`  | Identifies this optimizer process. When it changes, the optimizer restarted and `seq` started again at 1: drop your `since` and read the newest entries. |

A `since` or `limit` that is not a whole number is a 400.

## WebSocket endpoints

WebSocket endpoints provide real-time streaming data. All three endpoints follow
the same connection lifecycle:

1. Client connects via HTTP upgrade to the WebSocket path
2. If auth is configured, client sends `{"auth": "my-token"}` as first message
3. Server sends initial snapshot
4. Server pushes updates at regular intervals

### Connection limits

| Parameter                                  | Value |
| ------------------------------------------- | ----- |
| Max WebSocket connections (all streams)     | 8     |
| Max connections awaiting authentication     | 16    |
| … of which from any one remote address      | 4     |
| Ping interval                               | 30s   |
| Pong timeout                                | 10s   |
| Auth timeout                                | 2s    |

The "max connections awaiting authentication" limit is counted separately
from the overall connection cap above (which counts every stream
together, not per endpoint): at most 16 WebSocket connections may be
simultaneously holding a slot while waiting for the in-band
`{"auth": "..."}` message (see [Authentication Modes](#authentication-modes)),
and at most 4 of those may share one remote address — enough for a client
to open several streams at once (the bundled web console opens two per
browser tab, statistics and log) while it authenticates, without a single
never-authenticating address being able to take every slot for everyone
else. Connections waiting to authenticate also count toward the overall cap
of 8, which is reached first: in practice at most 8 can be waiting at once,
and the limit of 16 applies only where the overall cap is higher than 16.
From one address the limit of 4 is the one that applies. Clients that reach
the optimizer through the same proxy or address share those 4 slots; an
honest client holds one only until its token arrives. Connections on the
unix socket need no token, so they never wait to authenticate and never
count against these limits.
A connection that is already authenticated — including one pre-authenticated
under `--api-read-open` on an allow-listed stream — never counts against
this budget, so it only bounds the number of handshakes that have completed
but not yet proven a token. An upgrade that would exceed it is refused the
same way exceeding the overall connection cap is. A well-behaved client
does not keep retrying a stream the server has rejected for a missing or
wrong token: the shipped web console opens every stream immediately
(correct for the common case, since most deployments serve at least some
streams with no token at all) and, if a stream it opened this way is
closed for an authentication reason, waits for a new token rather than
reconnecting into the same rejection.

### GET /v1/ws/stats

Live server statistics with delta compression. Sends a full snapshot on connect,
then periodic deltas containing only changed fields.

```javascript
const ws = new WebSocket('ws://localhost:9880/v1/ws/stats');

// If auth is configured:
ws.onopen = () => ws.send(JSON.stringify({ auth: 'my-token' }));

ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  if (msg.type === 'snapshot') {
    // Full stats object (same schema as GET /v1/stats)
    console.log('Full stats:', msg.data);
  } else if (msg.type === 'delta') {
    // Only fields that changed since last message
    console.log('Changed:', msg.data);
  }
};
```

**Server messages:**

| Type       | Description                                                                       |
| ---------- | --------------------------------------------------------------------------------- |
| `snapshot` | Full stats on connect: `{type: "snapshot", sequence: N, data: StatsResponse}`     |
| `delta`    | Changed fields only: `{type: "delta", sequence: N, data: Partial<StatsResponse>}` |

**Client messages:**

| Message                  | Description                                            |
| ------------------------ | ------------------------------------------------------ |
| `{"auth": "token"}`      | Authenticate (required when auth is configured)        |
| `{"set_interval_ms": N}` | Change push interval (100ms - 60000ms, default 1000ms) |

Sequence numbers increment per message for loss detection. Delta compression
reduces typical message size from ~50 KB to ~1 KB.

### GET /v1/ws/events

Real-time optimization events. Events are batched at 100ms intervals.

```javascript
const ws = new WebSocket('ws://localhost:9880/v1/ws/events');
ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  if (msg.type === 'event') {
    console.log(msg.event_type, msg.detail);
  } else if (msg.type === 'overflow') {
    console.log('Dropped', msg.dropped_count, 'events');
  }
};
```

**Server messages:**

| Type       | Description                                                                               |
| ---------- | ----------------------------------------------------------------------------------------- |
| `event`    | `{type: "event", sequence: N, timestamp: MS, event_type: "...", detail: {...}}`           |
| `overflow` | `{type: "overflow", dropped_count: N}` -- oldest events dropped when buffer exceeds 64 KB |

**Event types:**

| Event            | Description                           |
| ---------------- | ------------------------------------- |
| `svg_candidacy`  | Image evaluated for SVG vectorization |
| `svg_vectorized` | SVG vectorization completed           |
| `svg_written`    | SVG variant written to cache          |

### GET /v1/ws/logs

Real-time log streaming. Sends the ring buffer contents (up to 2000 entries) on
connect, then streams new log entries as they occur.

```javascript
const ws = new WebSocket('ws://localhost:9880/v1/ws/logs');
ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  if (msg.type === 'snapshot') {
    console.log('History:', msg.entries.length, 'entries');
  } else if (msg.type === 'log') {
    console.log(`[${msg.level}] ${msg.module}: ${msg.message}`);
  }
};
```

**Server messages:**

| Type       | Description                                                                                                                           |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `snapshot` | Ring buffer on connect: `{type: "snapshot", entries: LogEntry[], total: N}`                                                              |
| `log`      | Single log entry: `{type: "log", seq: N, timestamp: MS, source: "...", level: "...", module: "...", message: "...", details?: {...}}` |
| `overflow` | Entries this client was not sent: `{type: "overflow", dropped_count: N, first_seq: A, last_seq: B}`                                      |

Every entry carries `seq`, a sequence number that increases by one per entry
for as long as the optimizer process runs (the first entry is `seq` 1, and
numbering starts again at 1 after a restart, so `since=0` always reads from
the beginning). `message` is always valid UTF-8 — bytes that are not are shown as
U+FFFD — and its content is capped at 4 KiB: a longer message keeps its first
4 KiB (cut on a character boundary) followed by a `…[truncated N bytes]`
suffix, so a truncated message is slightly longer than 4 KiB overall.

New entries are sent in batches (about every 100 ms), one `log` message per
entry, in `seq` order, and as fast as the client reads them. Every entry the
optimizer still holds reaches the client: the stream reads from the same ring
of the most recent 2000 entries that the snapshot and
[`GET /v1/logs`](#get-v1logs) read from. A client only misses entries that
left that ring before it could be sent them — it reads too slowly, or more
than 2000 entries arrived at once. It then receives one `overflow` message in
their place: `dropped_count` entries, `seq` `first_seq` through `last_seq`,
were not sent, and the next `log` message is `last_seq + 1`. Those entries are
gone from `GET /v1/logs` as well, which reports them as a `gap`. A client
that does not need the exact range can read `dropped_count` alone.

Under `--api-read-open` with a token configured, this stream still requires
it: the handshake succeeds, but the connection is closed unless the token
arrives as the first message within the auth timeout — the same step every
client already uses to authenticate (see
[Authentication Modes](#authentication-modes)). Over the unix socket, and on
a tokenless API opened with `--api-no-auth`, the stream is open.

**Log sources:** `worker`, `cache`, `chrome`

**Log levels:** `debug`, `info`, `warning`, `error`

